## TCP ? UDP ?

[L4 vs L7](https://problem-child.tistory.com/128) 글에서 L4 는 **전송 계층**이라고 했다.
그 전송 계층의 대표 프로토콜이 바로 **TCP** 와 **UDP** 다.

둘 다 데이터를 상대방에게 보내는 방법인데, 성격이 정반대다.

- **TCP** : 등기우편. 받았는지 **확인 서명**까지 받는다
- **UDP** : 전단지. 일단 **뿌리고 끝**이다

---

## 전송 계층이 하는 일

IP (3계층) 는 데이터를 **어느 컴퓨터로** 보낼지 정한다.
전송 계층 (4계층) 은 그 컴퓨터의 **어느 프로그램으로** 보낼지 정한다. 그게 **포트 번호**다.

```
192.168.0.10:443   → 이 컴퓨터의 443 포트 (웹 서버)
192.168.0.10:5432  → 이 컴퓨터의 5432 포트 (DB)
```

여기에 **어떻게 보낼지** (꼼꼼하게 ? 빠르게 ?) 를 정하는 게 TCP 와 UDP 의 차이다.

---

## TCP : 등기우편

**연결을 먼저 맺고**, 보낸 데이터가 **제대로 도착했는지 확인**하는 방식

### 1. 연결 맺기 : 3-way Handshake

데이터를 보내기 전에 세 번 인사를 주고받는다.

```
클라이언트                         서버
    │ ── SYN ───────────────────→ │   "연결해도 돼 ?"
    │ ←──────────────── SYN+ACK ── │   "응, 나도 연결할게"
    │ ── ACK ───────────────────→ │   "확인 ! 이제 보낸다"
    │                              │
    │ ====== 데이터 주고받기 ====== │
```

- SYN (Synchronize) : 연결 요청
- ACK (Acknowledgment) : 확인 응답

### 2. 확인 응답과 재전송

데이터를 보내면 받는 쪽이 **"받았어 (ACK)"** 라고 답한다.
일정 시간 안에 답이 없으면 **다시 보낸다.**

```
보냄 : 1번 조각 → ACK 옴 ✅
보냄 : 2번 조각 → (중간에 사라짐) → ACK 안 옴 → 2번 다시 보냄 ✅
```

### 3. 순서 보장

데이터에 **순서 번호 (Sequence Number)** 를 붙여서 보낸다.
네트워크 사정으로 3번이 2번보다 먼저 도착해도, 받는 쪽에서 **순서대로 다시 맞춘다.**

```
도착 순서 : 1 → 3 → 2
전달 순서 : 1 → 2 → 3   (번호 보고 재정렬)
```

### 4. 흐름 제어 , 혼잡 제어

- **흐름 제어** : 받는 쪽이 처리할 수 있는 만큼만 보낸다 (받는 쪽이 "지금 이만큼 받을 수 있어" 라고 알려줌)
- **혼잡 제어** : 네트워크가 막히면 보내는 속도를 줄인다

### 5. 연결 끊기 : 4-way Handshake

끊을 때도 서로 확인한다.

```
클라이언트 ── FIN ──→ 서버      "나 다 보냈어"
클라이언트 ←── ACK ── 서버      "알았어"
클라이언트 ←── FIN ── 서버      "나도 다 보냈어"
클라이언트 ── ACK ──→ 서버      "알았어, 끝 !"
```

### 정리하면

- 데이터가 **빠짐없이 , 순서대로** 도착한다
- 대신 인사 , 확인 , 재전송 때문에 **느리고 무겁다**

등기우편처럼 확실하지만, 서명 받는 데 시간이 걸린다.

## UDP : 전단지

**연결 없이** 그냥 보내는 방식

```
클라이언트 ── 데이터 ──→ 서버
클라이언트 ── 데이터 ──→ 서버
클라이언트 ── 데이터 ──→ 서버
(받았는지 안 받았는지 신경 안 씀)
```

- 연결을 맺지 않는다 (인사 없음)
- 도착했는지 확인하지 않는다 (ACK 없음)
- 사라져도 다시 보내지 않는다 (재전송 없음)
- 순서가 뒤바뀌어도 그대로 전달한다

그래서 **빠르고 가볍다.**
헤더 크기만 봐도 차이가 난다.

| | TCP | UDP |
|---|---|---|
| 헤더 크기 | 20 ~ 60 바이트 | **8 바이트** |

UDP 헤더에는 출발 포트 , 도착 포트 , 길이 , 체크섬 딱 네 개만 들어 있다.
(체크섬으로 데이터가 깨졌는지는 확인할 수 있지만, 깨졌다고 다시 달라고 하지는 않는다)

전단지는 몇 장 날아가도 신경 안 쓰고, 일단 많이 빨리 뿌리는 게 중요하다.

## 데이터 몇 개 빠져도 괜찮다고 ?

UDP 가 쓸모없어 보일 수 있지만, **늦게 오는 것보다 안 오는 게 나은** 경우가 있다.

### 실시간 영상 통화

1초 전 화면 조각이 늦게 도착하면 ?
이미 지나간 장면이라 의미가 없다. 다시 받느라 기다리는 것보다 **그냥 넘기고 지금 화면을 보여주는 게** 낫다.

### 온라인 게임

캐릭터 위치는 계속 새로 온다.
0.1초 전 위치를 다시 받느라 화면이 멈추면, 그게 더 큰 문제다.

### DNS

"naver.com 의 IP 가 뭐야 ?" 같은 **짧은 질문 , 짧은 답**
TCP 처럼 인사 세 번 하는 것보다 그냥 물어보고, 답이 없으면 다시 물어보는 게 빠르다.
(응답이 너무 크면 TCP 로 다시 물어보기도 한다)

## 코드로 보는 차이 (Node.js)

### TCP

```javascript
const net = require("net");

// 서버 : 연결이 들어오면 받은 데이터를 그대로 돌려줌
const server = net.createServer((socket) => {
  socket.on("data", (data) => socket.write(`echo: ${data}`));
});
server.listen(4000);

// 클라이언트 : 먼저 연결하고 (connect) 보낸다
const client = net.connect(4000, () => client.write("hello"));
client.on("data", (data) => {
  console.log(data.toString()); // echo: hello
  client.end();
  server.close();
});
```

`connect` 로 **연결을 먼저 맺고** , 그 연결 위에서 데이터를 주고받는다.

### UDP

```javascript
const dgram = require("dgram");

// 서버 : 데이터가 오면 보낸 주소로 그대로 돌려줌
const server = dgram.createSocket("udp4");
server.on("message", (msg, rinfo) => {
  server.send(`echo: ${msg}`, rinfo.port, rinfo.address);
});
server.bind(4001);

// 클라이언트 : 연결 없이 주소만 정해서 바로 보낸다
const client = dgram.createSocket("udp4");
client.on("message", (msg) => {
  console.log(msg.toString()); // echo: hello
  client.close();
  server.close();
});
client.send("hello", 4001, "127.0.0.1");
```

`connect` 가 없다. 보낼 때마다 **주소와 포트를 붙여서** 그냥 던진다.

## HTTP/3 는 UDP 를 쓴다 ?

웹은 원래 TCP 위에서 동작했다 (HTTP/1.1 , HTTP/2).
그런데 최신 **HTTP/3** 는 **UDP 기반의 QUIC** 프로토콜을 쓴다.

UDP 는 신뢰성이 없다면서 왜 ?

- TCP 는 운영체제에 박혀 있어서 고치기가 어렵다
- TCP 는 패킷 하나가 늦으면 **뒤에 있는 데이터 전부 기다려야** 한다 (HOL Blocking)
- TCP + TLS 는 연결할 때 인사가 많아서 느리다

그래서 **빠른 UDP 위에, 재전송 , 순서 보장 , 암호화를 직접 다시 만든 것**이 QUIC 이다.
전단지 배달망을 쓰면서, 필요한 것만 직접 확인 서명을 받는 셈이다.

(HTTPS 의 암호화가 궁금하다면 [http vs https](https://problem-child.tistory.com/107) 글을 참고해 주세요)

## TCP vs UDP

| 항목 | TCP | UDP |
|---|---|---|
| 연결 | 연결형 (3-way Handshake) | 비연결형 |
| 신뢰성 | 보장 (ACK , 재전송) | 보장 안 함 |
| 순서 | 보장 (순서 번호) | 보장 안 함 |
| 흐름 / 혼잡 제어 | 있음 | 없음 |
| 속도 | 상대적으로 느림 | 빠름 |
| 헤더 크기 | 20 ~ 60 바이트 | 8 바이트 |
| 데이터 단위 | 바이트 스트림 (경계 없음) | 데이터그램 (보낸 단위 그대로) |
| 1:N 전송 | 불가 (1:1) | 브로드캐스트 , 멀티캐스트 가능 |
| 사용 예 | HTTP/1.1 , HTTP/2 , SSH , 이메일 , DB 연결 | DNS , 영상 통화 , 게임 , 스트리밍 , HTTP/3 (QUIC) |
| 비유 | 등기우편 | 전단지 |

---

## 정리

- TCP 와 UDP 는 **전송 계층 (L4)** 의 대표 프로토콜이다
- **TCP** 는 연결을 맺고 , 확인하고 , 다시 보내고 , 순서를 맞춘다 → **정확하지만 느리다**
- **UDP** 는 그냥 보낸다 → **빠르지만 빠지거나 뒤섞일 수 있다**
- 빠짐없이 와야 하면 TCP (웹 페이지 , 파일 , 결제)
- 늦게 오느니 안 오는 게 나으면 UDP (영상 통화 , 게임)
- 요즘은 UDP 위에 필요한 기능만 다시 얹는 방식 (QUIC , HTTP/3) 도 많이 쓴다

꼭 받아야 하는 서류는 등기로, 많이 빨리 알려야 하는 소식은 전단지로.
