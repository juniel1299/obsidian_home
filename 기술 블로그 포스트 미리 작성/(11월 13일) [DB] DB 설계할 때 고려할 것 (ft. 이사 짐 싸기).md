## 테이블부터 만들면 안 되는 이유

DB 설계라고 하면 바로 `CREATE TABLE` 부터 치고 싶어진다.
그런데 설계가 잘못되면 나중에 고치기가 제일 어려운 게 DB 다.
코드는 배포하면 바뀌지만, **이미 쌓인 데이터는 그대로 남기 때문**이다.

이사 짐 싸기로 생각하면 쉽다.

- 새 집에서 **어떻게 살지** 먼저 정하고
- 같은 물건은 **한 박스에만** 넣고
- 박스마다 **번호와 라벨**을 붙이고
- 이사 첫날 쓸 물건은 **따로 꺼내 두기 쉽게** 싼다

이번 글은 DB 를 설계할 때 고려할 것들을 순서대로 정리한다.

---

## 1. 요구사항 : 어떻게 살지 먼저

설계는 보통 이 순서로 진행한다.

| 단계 | 하는 일 | 결과물 |
|---|---|---|
| 요구사항 분석 | 어떤 데이터를 , 누가 , 어떻게 쓰는지 정리 | 기능 목록 , 화면 |
| 개념적 설계 | 엔티티 (사물) 와 관계 찾기 | ERD |
| 논리적 설계 | 테이블 , 컬럼 , 키 , 정규화 | 테이블 정의서 |
| 물리적 설계 | 실제 DB 에 맞춘 타입 , 인덱스 , 용량 | DDL (CREATE 문) |

요구사항 단계에서 확인할 질문

- 어떤 **명사**가 나오나 ? (회원 , 상품 , 주문) → 테이블 후보
- 서로 어떤 **관계**인가 ? (회원 1명이 주문 여러 개 = 1:N)
- 어떤 **화면 / 조회**가 자주 일어나나 ? (내 주문 목록 , 상품 검색)
- 데이터가 **얼마나 쌓이나 ?** (하루 주문 100건 ? 100만 건 ?)

마지막 두 개를 빼먹기 쉽다.
이 질문의 답이 뒤에 나오는 **인덱스 , 반정규화**를 정한다.

## 2. 정규화 : 같은 물건은 한 박스에만

정규화는 **중복을 없애서 데이터가 서로 어긋나지 않게** 하는 과정이다.

### 정규화를 안 하면 생기는 일

주문을 테이블 하나에 몰아넣었다고 해 보자.

| 주문번호 | 고객명 | 고객전화 | 상품 | 상품가격 |
|---|---|---|---|---|
| 100 | 철수 | 010-1111-2222 | 키보드 | 50000 |
| 101 | 철수 | 010-1111-2222 | 마우스 | 20000 |
| 102 | 영희 | 010-3333-4444 | 키보드 | 50000 |

세 가지 문제 (이상 현상) 가 생긴다.

- **수정 이상** : 철수 전화번호가 바뀌면 **모든 행**을 고쳐야 한다. 하나라도 빠뜨리면 철수 번호가 두 개가 된다
- **삽입 이상** : 아직 주문이 없는 상품은 **넣을 자리가 없다**
- **삭제 이상** : 영희의 주문을 지우면 **영희라는 고객 정보도 같이 사라진다**

같은 물건을 박스 여러 개에 나눠 담으면, 하나를 버릴 때 다른 걸 같이 버리는 셈이다.

### 제1정규형 (1NF) : 칸에는 값 하나만

```
❌ 상품 : "키보드, 마우스"
```

한 칸에 여러 값을 넣지 않는다.
이렇게 넣으면 "마우스를 산 주문" 을 찾기도 , 수량을 따로 적기도 어렵다.
→ 주문 상품을 **행으로 나눈다** (주문 상품 테이블)

### 제2정규형 (2NF) : 키 전체에 의존

주문 상품 테이블의 키가 (주문번호 , 상품번호) 라고 하자.

| 주문번호 | 상품번호 | 상품명 | 수량 |
|---|---|---|---|

`상품명` 은 주문번호와 상관없이 **상품번호만** 알면 정해진다.
키의 **일부에만** 의존하는 컬럼이다 (부분 함수 종속).
→ 상품명은 **상품 테이블로 분리**한다

### 제3정규형 (3NF) : 키가 아닌 컬럼끼리 의존하지 않기

| 주문번호 | 고객번호 | 고객명 | 고객전화 |
|---|---|---|---|

`고객명` 은 주문번호가 아니라 **고객번호**에 따라 정해진다.
주문번호 → 고객번호 → 고객명 처럼 **건너서** 의존한다 (이행 함수 종속).
→ 고객 정보는 **고객 테이블로 분리**한다

### 결과

```
customers (고객)      products (상품)
     │ 1                   │ 1
     │                     │
     │ N                   │ N
orders (주문) ── 1:N ── order_items (주문 상품)
```

실무에서는 보통 **3정규형까지** 맞추고 시작한다.
(BCNF , 4NF , 5NF 도 있지만 대부분 3NF 에서 해결된다)

## 3. 키 : 박스 번호 붙이기

### 기본 키 (PK) 는 바뀌지 않는 값으로

| 종류 | 예시 | 장점 | 단점 |
|---|---|---|---|
| 자연 키 | 이메일 , 전화번호 , 주민번호 | 의미가 있음 | **바뀔 수 있고** , 개인정보가 키가 됨 |
| 대리 키 | 자동 증가 숫자 , UUID | 절대 안 바뀜 | 의미가 없음 |

전화번호를 PK 로 쓰면 , 번호가 바뀌는 순간 그 번호를 참조하는 **모든 테이블**을 고쳐야 한다.
그래서 PK 는 보통 **대리 키**로 두고 , 이메일 / 전화번호는 `UNIQUE` 로 중복만 막는다.

### 외래 키 (FK) 로 관계를 보장

`orders.customer_id` 가 `customers` 에 **실제로 있는 고객**인지 DB 가 확인해 준다.
없는 고객의 주문 같은 **고아 데이터**가 생기지 않는다.

(테이블을 다시 합쳐서 조회하는 방법은 [inner ? outer ?](https://problem-child.tistory.com/111) 글을 참고해 주세요)

## 4. 타입과 제약조건 : 박스에 라벨 붙이기

정규화를 거친 테이블을 DDL 로 옮기면 이렇게 된다.

```sql
CREATE TABLE customers (
  customer_id  INTEGER       PRIMARY KEY,
  name         VARCHAR(50)   NOT NULL,
  phone        VARCHAR(20)   NOT NULL UNIQUE,
  created_at   TIMESTAMP     DEFAULT CURRENT_TIMESTAMP NOT NULL
);

CREATE TABLE products (
  product_id   INTEGER       PRIMARY KEY,
  name         VARCHAR(100)  NOT NULL,
  price        DECIMAL(12,2) NOT NULL CHECK (price >= 0)
);

CREATE TABLE orders (
  order_id     INTEGER       PRIMARY KEY,
  customer_id  INTEGER       NOT NULL REFERENCES customers (customer_id),
  status       VARCHAR(20)   DEFAULT 'PAID' NOT NULL
                             CHECK (status IN ('PAID', 'SHIPPED', 'CANCELED')),
  ordered_at   TIMESTAMP     DEFAULT CURRENT_TIMESTAMP NOT NULL
);

CREATE TABLE order_items (
  order_id     INTEGER       NOT NULL REFERENCES orders (order_id),
  product_id   INTEGER       NOT NULL REFERENCES products (product_id),
  quantity     INTEGER       NOT NULL CHECK (quantity > 0),
  unit_price   DECIMAL(12,2) NOT NULL,  -- 주문 당시 가격
  PRIMARY KEY (order_id, product_id)
);
```

(Oracle 이라면 `VARCHAR2` , `NUMBER` 를 쓰고 , 자동 증가는 `GENERATED AS IDENTITY` 로 만든다)

### 제약조건은 DB 가 지키는 규칙

| 제약조건 | 막아주는 것 |
|---|---|
| NOT NULL | 비어 있으면 안 되는 값이 비는 것 |
| UNIQUE | 같은 전화번호로 두 번 가입 |
| CHECK | 수량 0 개 , 없는 주문 상태 |
| FOREIGN KEY | 없는 고객의 주문 |
| DEFAULT | 값을 안 넣었을 때 기본값 |

직접 넣어 보면 DB 가 막는다.

```sql
INSERT INTO orders (order_id, customer_id) VALUES (101, 999);
-- FOREIGN KEY constraint failed

INSERT INTO order_items VALUES (100, 1, 0, 50000);
-- CHECK constraint failed: quantity > 0

INSERT INTO orders (order_id, customer_id, status) VALUES (102, 1, 'LOST');
-- CHECK constraint failed: status IN ('PAID', 'SHIPPED', 'CANCELED')
```

(에러 문구는 SQLite 로 실행한 결과다. DB 마다 문구는 다르다)

"애플리케이션에서 검사하면 되지 않나 ?" 싶지만 ,
DB 에는 관리자 툴 , 배치 , 다른 서비스 등 **여러 길로 데이터가 들어온다.**
마지막 방어선은 DB 에 두는 게 안전하다.

### 타입 고를 때 주의할 것

- **금액은 DECIMAL (NUMBER)** : FLOAT / DOUBLE 은 0.1 + 0.2 가 정확히 0.3 이 안 되는 오차가 있다
- **날짜는 날짜 타입** : 문자열 '2026-11-13' 로 저장하면 정렬 , 계산 , 검증이 다 불편하다
- **길이는 넉넉하되 근거 있게** : 이름 VARCHAR(4000) 은 의도를 알 수 없다
- **시간대 기준 통일** : 서버마다 시간대가 다르면 같은 주문의 시각이 다르게 보인다

### unit_price 는 중복 아닌가 ?

`products.price` 가 있는데 `order_items.unit_price` 를 또 둔 이유

상품 가격은 나중에 바뀐다.
실제로 키보드 가격을 50000 → 55000 으로 바꾸고 조회해 보면

| 주문번호 | 상품 | 주문 당시 가격 (unit_price) | 현재 가격 (price) |
|---|---|---|---|
| 100 | 키보드 | 50000 | 55000 |

주문 당시 가격이 없으면 , 지난 주문의 결제 금액이 **멋대로 바뀐다.**
이건 중복이 아니라 **그 시점의 사실을 기록**하는 것이다.
"같은 값인가 ?" 보다 **"같은 의미인가 ?"** 를 보고 판단해야 한다.

## 5. 조회 패턴과 인덱스 : 박스 목록표

정규화는 **저장**을 깔끔하게 만든다.
하지만 서비스는 대부분 **조회**를 훨씬 많이 한다.

그래서 "자주 하는 조회" 에 맞춰 인덱스를 설계한다.

```sql
-- 자주 하는 조회 : 내 주문 목록 , 최신순
SELECT * FROM orders WHERE customer_id = 1 ORDER BY ordered_at DESC;

-- 그 조회에 맞춘 인덱스
CREATE INDEX idx_orders_customer_date ON orders (customer_id, ordered_at);
```

실행 계획을 보면 인덱스를 탄다.

```
SEARCH orders USING INDEX idx_orders_customer_date (customer_id=?)
```

인덱스를 고를 때 기준

- WHERE , JOIN , ORDER BY 에 **자주** 쓰이는 컬럼
- 여러 컬럼이면 **= 조건 컬럼을 앞에** , 범위 / 정렬 컬럼을 뒤에
- FK 컬럼 (`orders.customer_id`) 은 JOIN 에 자주 쓰이니 인덱스 후보 (Oracle 은 FK 에 인덱스를 자동으로 만들지 않는다)

인덱스는 많을수록 좋은 게 아니다.
INSERT / UPDATE 때마다 인덱스도 같이 고쳐야 해서 **쓰기가 느려진다.**

(인덱스의 원리와 단점은 [Index 란 ?](https://problem-child.tistory.com/122) 글을 참고해 주세요)

## 6. 반정규화 : 첫날 쓸 물건은 따로

정규화를 하면 테이블이 잘게 나뉘고 , 조회할 때 **JOIN 이 늘어난다.**
데이터가 많아져서 JOIN 이 너무 느려지면 , 일부러 중복을 허용한다. 이게 반정규화다.

| 방법 | 예시 |
|---|---|
| 컬럼 중복 | 주문 테이블에 고객명을 같이 저장 |
| 계산 값 저장 | 주문 테이블에 총 금액 저장 (매번 SUM 안 하기) |
| 요약 테이블 | 일별 매출 테이블을 따로 만들어 집계 결과 저장 |

이사 첫날 쓸 칫솔은 욕실 박스에도 있지만 , 가방에 하나 더 챙기는 것과 같다.

대신 대가가 있다.

- 원본이 바뀌면 **복사본도 같이** 고쳐야 한다
- 깜빡하면 데이터가 서로 어긋난다 (정규화로 없앤 문제가 돌아온다)

그래서 순서가 중요하다.

```
정규화 → 실제로 느린 조회를 확인 → 인덱스 , 쿼리 개선 → 그래도 안 되면 반정규화
```

처음부터 "느릴 것 같아서" 반정규화하면 안 된다.

(요약 테이블과 비슷한 개념인 Materialized View 는 [View vs Snapshot](https://problem-child.tistory.com/116) 글을 참고해 주세요)

## 7. 그 밖에 미리 정해 둘 것

### 삭제 정책

| 방식 | 동작 | 언제 |
|---|---|---|
| 물리 삭제 (Hard Delete) | DELETE 로 진짜 삭제 | 다시 볼 일 없는 데이터 |
| 논리 삭제 (Soft Delete) | `deleted_at` 컬럼에 시간만 기록 | 복구 , 이력이 필요한 데이터 |

논리 삭제는 **모든 조회에 `deleted_at IS NULL` 조건**이 붙어야 한다.
UNIQUE 제약 (탈퇴한 사람의 이메일로 재가입) 도 같이 고민해야 한다.

### 공통 컬럼

`created_at` , `updated_at` 처럼 언제 만들고 고쳤는지 기록하는 컬럼은 처음부터 넣어 두자.
문제가 생겼을 때 **"언제부터 이랬지 ?"** 를 추적할 수 있다.

### 이름 규칙

- 테이블 / 컬럼 이름 규칙을 통일 (`snake_case` , 단수 / 복수)
- 같은 의미는 같은 이름 (`customer_id` 를 어떤 테이블에선 `cust_no` 로 쓰지 않기)

### 데이터 증가

- 1년 뒤 몇 건이 될지 대략 계산해 본다
- 로그 , 이력처럼 계속 쌓이는 테이블은 **보관 기간**이나 **파티셔닝**을 미리 생각한다

### 꼭 RDB 여야 할까

구조가 자주 바뀌는 데이터 , 키로만 조회하는 대량 데이터는 NoSQL 이 더 맞을 수 있다.
(차이는 [Redis vs MongoDB vs DynamoDB](https://problem-child.tistory.com/132) 글을 참고해 주세요)

## 설계 체크리스트

| 단계 | 확인할 것 | 놓치면 |
|---|---|---|
| 요구사항 | 엔티티 , 관계 , 자주 하는 조회 , 데이터 양 | 엉뚱한 구조 |
| 정규화 | 3NF 까지 , 한 칸에 값 하나 | 수정 / 삽입 / 삭제 이상 |
| 키 | 안 바뀌는 PK , FK 로 관계 보장 | 키 변경 지옥 , 고아 데이터 |
| 제약조건 | NOT NULL , UNIQUE , CHECK | 잘못된 데이터 유입 |
| 타입 | 금액은 DECIMAL , 날짜는 날짜 타입 | 금액 오차 , 정렬 오류 |
| 이력 | 그 시점의 값 (주문 당시 가격) 저장 | 과거 데이터가 바뀜 |
| 인덱스 | 자주 하는 조회 기준으로 | 느린 조회 또는 느린 쓰기 |
| 반정규화 | 측정 후 , 최소한으로 | 데이터 불일치 |
| 운영 | 삭제 정책 , 공통 컬럼 , 이름 규칙 , 증가량 | 복구 불가 , 추적 불가 |

---

## 정리

- 설계는 **요구사항과 조회 패턴**부터 시작한다
- **정규화** (보통 3NF) 로 중복을 없애고 , 수정 / 삽입 / 삭제 이상을 막는다
- PK 는 **바뀌지 않는 대리 키** , 관계는 **FK** , 규칙은 **제약조건**으로 DB 가 지키게 한다
- 같은 값이어도 **의미가 다르면** 따로 저장한다 (주문 당시 가격)
- 인덱스는 **자주 하는 조회**에 맞추고 , 반정규화는 **측정한 뒤에** 최소한으로
- 삭제 정책 , 공통 컬럼 , 데이터 증가량도 처음에 정해 둔다

짐을 잘 싸 두면 , 이삿날보다 그 뒤에 사는 날들이 편하다.
