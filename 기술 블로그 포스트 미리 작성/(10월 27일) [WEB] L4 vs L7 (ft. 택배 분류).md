## L4 ? L7 ?

인프라 이야기를 듣다 보면 이런 말이 나온다.

> "앞단에 L4 두고, 그 뒤에 L7 로 라우팅해요"

여기서 L4 , L7 은 **OSI 7계층**의 4계층 , 7계층을 말한다.
보통은 **로드밸런서**가 몇 계층의 정보를 보고 트래픽을 나누는지를 뜻한다.

택배 분류로 생각하면 쉽다.

- **L4** : 상자에 붙은 **주소만** 보고 분류한다 (상자는 안 뜯음)
- **L7** : 상자를 **뜯어서 내용물까지** 보고 분류한다

---

## OSI 7계층 , 간단하게

| 계층 | 이름 | 하는 일 | 예시 |
|---|---|---|---|
| 7 | 응용 (Application) | 실제 데이터의 의미 | HTTP , HTTPS , DNS |
| 6 | 표현 (Presentation) | 인코딩 , 암호화 | TLS (보통 여기로 설명) |
| 5 | 세션 (Session) | 연결 유지 | |
| 4 | 전송 (Transport) | 포트 , 신뢰성 있는 전송 | **TCP , UDP** |
| 3 | 네트워크 (Network) | 경로 찾기 | **IP** |
| 2 | 데이터 링크 (Data Link) | 같은 네트워크 안 전달 | MAC , 이더넷 |
| 1 | 물리 (Physical) | 전기 신호 | 케이블 |

이번 글에서 중요한 건 두 개다.

- **4계층** : IP 주소 + **포트 번호** (TCP / UDP)
- **7계층** : **HTTP 내용** (URL , 헤더 , 쿠키 등)

```
[ IP 헤더 | TCP 헤더 | HTTP 요청 (GET /api/users , Host , Cookie ...) ]
  ←── L4 는 여기까지 ──→
  ←────────────── L7 은 끝까지 다 본다 ──────────────→
```

---

## 로드밸런서는 왜 필요할까 ?

서버 한 대로 모든 요청을 받으면

- 사용자가 늘면 버티지 못한다
- 그 서버가 죽으면 서비스 전체가 죽는다

그래서 서버를 여러 대 두고, 앞에서 **요청을 나눠주는 역할**을 둔다. 이게 로드밸런서다.

```
               ┌→ 서버 A
사용자 → 로드밸런서 ├→ 서버 B
               └→ 서버 C
```

이때 **무엇을 보고 나눠주느냐**에 따라 L4 와 L7 로 갈린다.

---

## L4 로드밸런서 : 주소만 보고 분류

**IP 와 포트**만 보고 서버를 고른다.

```
요청 : 203.0.113.10:443 으로 TCP 연결
→ "443 포트네 ? 서버 A , B , C 중에 하나로 보내자"
```

- 패킷 안의 HTTP 내용은 **보지 않는다** (볼 수도 없다)
- 그래서 **빠르고 가볍다**
- HTTP 가 아닌 트래픽도 다 처리한다 (DB , 게임 서버 , 채팅 등 TCP / UDP 전부)
- HTTPS 도 암호화된 채로 그대로 넘긴다 (복호화는 뒤의 서버가 한다)

할 수 없는 것

- /api 는 A 서버 , /images 는 B 서버 같은 **URL 기반 분기**
- 쿠키 , 헤더를 보고 판단하기

택배 기사님이 상자에 적힌 **동 이름**만 보고 트럭을 나누는 것과 같다.
빠르지만, 상자 안에 뭐가 들었는지는 모른다.

예시 : AWS NLB (Network Load Balancer) , HAProxy TCP 모드 , Nginx stream

---

## L7 로드밸런서 : 뜯어보고 분류

**HTTP 요청 내용**까지 보고 서버를 고른다.

```
GET /api/users       → API 서버로
GET /images/cat.png  → 이미지 서버로
Host: admin.site.com → 관리자 서버로
Cookie: ab_test=B    → 신버전 서버로
```

- URL 경로 , 도메인 (Host) , 헤더 , 쿠키 기반 라우팅 가능
- 같은 사용자를 같은 서버로 보내는 **쿠키 기반 고정 세션 (Sticky Session)**
- 악성 요청 차단 (WAF) , 캐싱 , 압축 같은 부가 기능
- HTTPS 내용을 보려면 **로드밸런서에서 복호화**해야 한다 (SSL / TLS 종료)

(HTTPS 암호화가 궁금하다면 [http vs https](https://problem-child.tistory.com/107) 글을 참고해 주세요)

단점

- 내용을 다 읽고 해석하니까 L4 보다 **느리고 무겁다**
- 복호화하려면 인증서도 로드밸런서에 둬야 한다

택배 분류 센터에서 상자를 **뜯어서** "이건 냉장 , 이건 깨지기 쉬움" 하고 나누는 것과 같다.
정확하지만 시간이 더 걸린다.

예시 : AWS ALB (Application Load Balancer) , Nginx , HAProxy HTTP 모드 , Envoy

## Nginx 로 보는 차이

Nginx 는 둘 다 할 수 있다.

### L7 : http 블록

```nginx
http {
    upstream api_servers {
        server 10.0.0.1:8080;
        server 10.0.0.2:8080;
    }

    upstream web_servers {
        server 10.0.0.3:3000;
    }

    server {
        listen 80;

        location /api/ {
            proxy_pass http://api_servers;  # /api 로 시작하면 API 서버로
        }

        location / {
            proxy_pass http://web_servers;  # 나머지는 웹 서버로
        }
    }
}
```

URL 경로 (location) 를 보고 나누고 있다. HTTP 를 읽어야 가능한 일이다.

### L4 : stream 블록

```nginx
stream {
    upstream game_servers {
        server 10.0.0.5:7777;
        server 10.0.0.6:7777;
    }

    server {
        listen 7777;
        proxy_pass game_servers;  # 7777 포트로 오면 그냥 나눠줌
    }
}
```

location 같은 게 없다. 포트로 들어오면 내용은 신경 쓰지 않고 넘긴다.

## 어떻게 나눠줄까 : 분배 방식

L4 , L7 둘 다 쓰는 방식들

| 방식 | 설명 |
|---|---|
| 라운드 로빈 (Round Robin) | A → B → C → A 순서대로 돌아가며 |
| 가중치 (Weighted) | 성능 좋은 서버에 더 많이 (A:3 , B:1) |
| 최소 연결 (Least Connections) | 지금 연결이 가장 적은 서버로 |
| IP 해시 (IP Hash) | 같은 IP 는 항상 같은 서버로 |

### 헬스 체크

죽은 서버로 요청을 보내면 안 되니까, 로드밸런서는 주기적으로 서버 상태를 확인한다.

- **L4** : 포트에 TCP 연결이 되는지만 확인 → 프로세스는 떠 있는데 앱이 고장 난 건 모를 수 있다
- **L7** : `/health` 같은 주소로 HTTP 요청을 보내서 **200 OK** 가 오는지 확인 → 더 정확하다

## L4 vs L7

| 항목 | L4 | L7 |
|---|---|---|
| 보는 정보 | IP , 포트 | URL , 헤더 , 쿠키 , HTTP 메서드 |
| 프로토콜 | TCP / UDP 전부 | HTTP / HTTPS (gRPC , WebSocket 포함) |
| 속도 | 빠름 | 상대적으로 느림 |
| 부하 | 가벼움 | 무거움 (내용 해석) |
| HTTPS | 암호화된 채로 통과 | 복호화 후 내용 확인 (TLS 종료) |
| URL 기반 라우팅 | 불가 | 가능 |
| 고정 세션 | IP 기준 | 쿠키 기준 |
| 헬스 체크 | TCP 연결 확인 | HTTP 응답 확인 |
| 부가 기능 | 거의 없음 | WAF , 캐싱 , 압축 , 헤더 수정 |
| 예시 | AWS NLB , Nginx stream | AWS ALB , Nginx http , Envoy |

## 그래서 언제 뭘 쓸까 ?

**L4 가 어울리는 경우**

- HTTP 가 아닌 트래픽 (DB , 게임 서버 , MQTT 등)
- 엄청난 트래픽을 최대한 빠르게 넘겨야 할 때
- 암호화를 끝까지 서버에서 처리해야 할 때

**L7 이 어울리는 경우**

- 마이크로서비스 (MSA) 처럼 URL 마다 다른 서비스로 보내야 할 때
- 도메인별로 서버를 나눌 때 (api.site.com , admin.site.com)
- A/B 테스트 , 카나리 배포처럼 쿠키나 헤더로 트래픽을 나눌 때

**둘 다 쓰는 경우도 많다**

```
사용자 → L4 (빠르게 분산) → L7 여러 대 (URL 로 라우팅) → 각 서비스
```

처음에 말한 "앞단에 L4 두고 , 뒤에 L7" 이 바로 이 구조다.
L4 가 대량의 연결을 빠르게 나눠주고, L7 이 내용을 보고 세밀하게 길을 찾아준다.

---

## 정리

- L4 , L7 은 OSI **4계층 (전송)** , **7계층 (응용)** 을 뜻한다
- **L4** 는 IP 와 포트만 보고 나눈다 → 빠르고 , 프로토콜을 가리지 않는다
- **L7** 은 HTTP 내용까지 보고 나눈다 → 느리지만 , URL / 헤더 / 쿠키로 똑똑하게 라우팅한다
- 실제 서비스는 **L4 + L7 을 같이** 쓰는 경우가 많다

주소만 보는 기사님과 상자를 뜯어보는 분류 센터, 둘 다 있어야 택배가 제대로 도착한다.
