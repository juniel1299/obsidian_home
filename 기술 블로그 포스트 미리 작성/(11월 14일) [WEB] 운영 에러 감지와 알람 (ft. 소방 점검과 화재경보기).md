## 테스트를 다 통과했는데 , 에러가 났다

"에러가 나면 어떻게 알아채나요 ?"

이 질문에 **"JUnit 으로 테스트합니다"** 라고 답하기 쉽다.
그런데 이건 질문과 조금 다른 답이다.

- **테스트 (JUnit , Jest)** : 배포 **전에** 코드가 맞는지 확인한다
- **모니터링** : 배포 **후에** 실제 서비스에서 생긴 문제를 알아챈다

건물로 생각하면 쉽다.

- **테스트** : 입주 전 **소방 점검**. 설계대로 지어졌는지 확인한다
- **모니터링** : 입주 후 **화재경보기**. 실제로 불이 나면 바로 울린다

소방 점검을 통과해도 불은 날 수 있다.
테스트로는 실제 사용자 , 실제 데이터 , 실제 트래픽에서 생기는 문제를 다 잡을 수 없기 때문이다.

이번 글은 배포한 뒤 **에러를 발견하고 알람을 받는 방법**을 정리한다.

---

## 테스트로는 못 잡는 것들

| 상황 | 예시 |
|---|---|
| 예상 못 한 입력 | 이름에 이모지 , 4000자짜리 주소 |
| 외부 서비스 장애 | 결제 API 가 갑자기 느려짐 |
| 환경 차이 | 운영 DB 에만 있는 오래된 데이터 |
| 트래픽 | 이벤트 날 접속자 100배 |
| 브라우저 | 특정 브라우저에서만 나는 화면 에러 |

그래서 운영에서는 **문제가 생기면 바로 보이게** 만드는 장치가 필요하다.

---

## 관측의 3가지 도구 : 로그 , 메트릭 , 트레이스

| 도구 | 알려주는 것 | 비유 | 대표 도구 |
|---|---|---|---|
| 로그 (Log) | **무슨 일이** 있었나 | 블랙박스 영상 | Logback , ELK , Loki |
| 메트릭 (Metric) | **얼마나** 자주 , 얼마나 느린가 | 계기판 | Prometheus , Grafana |
| 트레이스 (Trace) | 요청이 **어디를 거쳐** 갔나 | 택배 배송 조회 | OpenTelemetry , Zipkin |

여기에 **에러 추적 도구 (Sentry 등)** 와 **알람**을 더하면 기본 구성이 된다.

하나씩 보자.

---

## 1. 로그 : 블랙박스

가장 기본이다. 에러가 나면 **언제 , 어디서 , 왜** 났는지 기록한다.

### 로그 레벨

| 레벨 | 언제 | 예시 |
|---|---|---|
| ERROR | 처리 실패 , 바로 봐야 함 | 결제 실패 , DB 연결 끊김 |
| WARN | 실패는 아니지만 이상함 | 재시도 후 성공 , 느린 응답 |
| INFO | 정상 흐름의 주요 지점 | 주문 생성 , 로그인 |
| DEBUG | 개발용 상세 정보 | 쿼리 파라미터 |

운영에서는 보통 **INFO 이상**만 남긴다.
전부 ERROR 로 찍으면 정작 중요한 에러가 묻힌다.

### Spring 에서 한곳에 모으기

에러를 컨트롤러마다 잡지 말고 , 한곳에서 기록한다.

```java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ResponseEntity<String> handle(Exception e, HttpServletRequest request) {
        // 스택 트레이스까지 남기려면 예외 객체를 마지막 인자로 넘긴다
        log.error("처리 실패 : {} {}", request.getMethod(), request.getRequestURI(), e);

        return ResponseEntity.status(500).body("잠시 후 다시 시도해 주세요");
    }
}
```

- 사용자에게는 **간단한 메시지**만 보여준다 (내부 에러 내용을 그대로 보여주면 보안상 위험하다)
- 로그에는 **스택 트레이스까지** 자세히 남긴다

### 요청마다 번호 붙이기 (traceId)

동시에 요청이 수백 개 들어오면 , 로그가 뒤섞여서 어떤 줄이 같은 요청인지 알 수 없다.
그래서 요청마다 **고유 번호 (traceId)** 를 붙인다.

```
[traceId=a1b2c3] 주문 요청 시작
[traceId=x9y8z7] 상품 조회
[traceId=a1b2c3] 결제 API 호출
[traceId=a1b2c3] ERROR 결제 실패 : timeout
```

`a1b2c3` 만 검색하면 그 요청의 흐름이 한 번에 보인다.
(Spring 에서는 MDC 로 넣거나 , Micrometer Tracing 이 자동으로 넣어 준다)

### 로그에 넣으면 안 되는 것

비밀번호 , 토큰 , 카드 번호 , 주민번호 같은 개인정보는 **절대 로그에 남기지 않는다.**
로그는 생각보다 많은 사람과 시스템이 본다.

### 서버가 여러 대라면

서버마다 로그 파일을 들어가서 볼 수는 없다.
그래서 로그를 **한곳으로 모으는** 도구를 쓴다 (ELK , Loki , CloudWatch Logs 등).

## 2. 에러 추적 도구 : 화재 위치 알려주는 경보기

로그는 남기기만 한다. **누가 보러 가야** 안다.
에러 추적 도구는 에러가 나면 **알아서 모아서 알려준다.** 대표적인 게 Sentry 다.

해주는 일

- 같은 에러를 **하나로 묶어서** 몇 번 , 몇 명에게 났는지 보여준다
- 스택 트레이스 , 브라우저 , OS , 배포 버전을 같이 기록한다
- 에러 직전에 사용자가 **무엇을 클릭했는지** (breadcrumbs) 보여준다
- **새로운 에러**가 생기거나 , 갑자기 늘면 알람을 보낸다

### 프론트엔드 에러도 잡을 수 있다

서버 로그에는 **브라우저에서 난 에러가 안 남는다.**
사용자 화면이 하얗게 멈춰도 서버는 모른다.

```javascript
// Next.js : @sentry/nextjs
import * as Sentry from "@sentry/nextjs";

Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
  environment: "production",
  tracesSampleRate: 0.1,  // 성능 추적은 요청의 10% 만 샘플링
});
```

```javascript
// 직접 잡은 에러도 보낼 수 있다
try {
  await pay(order);
} catch (error) {
  Sentry.captureException(error);
  throw error;
}
```

(DSN 은 에러를 보낼 주소라서 브라우저에 공개돼도 되는 값이다. 대신 프로젝트 설정에서 허용 도메인을 제한해 두자)

### 소스맵

배포된 JS 는 압축돼 있어서 에러 위치가 `a.js:1:20387` 처럼 나온다.
**소스맵 (Source Map)** 을 에러 추적 도구에 올려 두면 원래 코드의 파일 , 줄 번호로 보여준다.
소스맵은 원본 코드가 드러나니 **공개 서버에는 올리지 않고** 도구에만 업로드한다.

## 3. 메트릭 : 계기판

로그와 에러 추적은 **하나하나의 사건**을 본다.
메트릭은 **숫자로 전체 상태**를 본다.

### 기본으로 볼 숫자 (RED)

| 지표 | 뜻 | 예시 |
|---|---|---|
| Rate | 초당 요청 수 | 평소 100 → 갑자기 0 이면 장애 |
| Errors | 에러 비율 | 5xx 응답이 5% 넘음 |
| Duration | 응답 시간 | p95 가 3초 넘음 |

**p95** 는 "요청 100개 중 느린 5개를 뺀 가장 느린 값" 이다.
평균은 대부분이 빠르면 몇 명이 엄청 느려도 티가 안 나서 , 보통 p95 , p99 를 본다.

여기에 서버 자원 (CPU , 메모리 , 디스크 , DB 커넥션 수) 을 같이 본다.

### Spring Boot 에서 메트릭 노출

```properties
# application.properties
management.endpoints.web.exposure.include=health,prometheus
```

`spring-boot-starter-actuator` 와 `micrometer-registry-prometheus` 를 추가하면
`/actuator/prometheus` 에서 요청 수 , 응답 시간 , JVM 메모리 같은 숫자가 나온다.
Prometheus 가 이 숫자를 주기적으로 가져가고 , Grafana 로 그래프를 그린다.

`/actuator/prometheus` 는 내부 정보가 많으니 **외부에서 접근하지 못하게** 막아 두자.

### 헬스 체크

`/actuator/health` 는 서버가 살아 있는지 알려준다.
로드밸런서는 이 주소로 죽은 서버를 골라낸다.
(로드밸런서의 헬스 체크는 [L4 vs L7](https://problem-child.tistory.com/128) 글을 참고해 주세요)

## 4. 트레이스 : 배송 조회

서비스가 여러 개로 나뉘어 있으면 , 느린 원인이 어디인지 찾기 어렵다.

```
사용자 → API 서버 (20ms) → 주문 서비스 (30ms) → 결제 서비스 (2800ms) ← 여기가 문제
```

트레이스는 요청 하나가 **어느 서비스를 거쳐 , 각각 얼마나 걸렸는지** 보여준다.
위의 traceId 가 서비스 사이를 따라다니면서 이 흐름을 이어 준다.

서버가 하나라면 로그 + 메트릭으로 충분한 경우가 많다.
서비스가 나뉘기 시작하면 OpenTelemetry 같은 표준으로 붙이는 걸 고려한다.

## 5. 알람 : 경보기가 울리게

모니터링 화면을 하루 종일 쳐다볼 수는 없다.
**문제가 생기면 사람을 부르는 장치**가 알람이다.

### Prometheus 알람 규칙 예시

```yaml
groups:
  - name: api
    rules:
      - alert: HighErrorRate
        # 최근 5분간 전체 요청 중 5xx 비율이 5% 초과
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
            / sum(rate(http_server_requests_seconds_count[5m])) > 0.05
        for: 5m   # 5분 동안 계속될 때만 알람
        labels:
          severity: critical
        annotations:
          summary: "5xx 에러 비율 5% 초과"
```

알람은 Slack , 이메일 , 전화 (PagerDuty 등) 로 받는다.

### 좋은 알람의 조건

알람이 너무 많으면 사람들이 **무시하기 시작한다.**
매일 오작동하는 화재경보기는 진짜 불이 나도 아무도 안 나간다.

| 원칙 | 설명 |
|---|---|
| 증상 기준 | "CPU 80%" 보다 **"사용자 에러율 5%"** 처럼 사용자가 느끼는 문제로 |
| 지속 시간 | 순간 튀는 값은 무시 (`for: 5m`) |
| 심각도 구분 | critical 은 바로 전화 , warning 은 업무 시간에 Slack |
| 행동 가능 | 알람을 받으면 **무엇을 해야 하는지** 알 수 있어야 함 |
| 중복 억제 | 같은 원인으로 알람 100개가 오지 않게 묶기 |

## 에러가 나면 , 실제 흐름

```
1. 알람 수신         : Slack 에 "5xx 비율 5% 초과" 알람
2. 범위 파악         : Grafana 로 언제부터 , 어떤 API 인지 확인
3. 원인 찾기         : Sentry 에서 새로 생긴 에러와 스택 트레이스 확인
4. 상세 확인         : traceId 로 해당 요청의 로그 검색
5. 대응              : 직전 배포가 원인이면 롤백 , 아니면 수정 배포
6. 재발 방지         : 원인 정리 + 이 상황을 잡는 테스트 추가
```

마지막 단계가 중요하다.
운영에서 발견한 에러는 **테스트로 만들어서** 다시는 같은 문제가 배포되지 않게 한다.
결국 모니터링과 테스트는 **서로를 채워 주는** 관계다.

---

## 테스트 vs 모니터링

| 항목 | 테스트 (JUnit , Jest) | 모니터링 (로그 , Sentry , Prometheus) |
|---|---|---|
| 시점 | 배포 전 | 배포 후 , 운영 중 |
| 대상 | 내가 예상한 상황 | 실제 사용자 , 실제 데이터 |
| 목적 | 버그를 미리 막기 | 생긴 문제를 빨리 알아채기 |
| 결과 | 통과 / 실패 | 로그 , 그래프 , 알람 |
| 못 잡는 것 | 예상 못 한 입력 , 외부 장애 , 트래픽 | 아직 배포 안 된 코드의 버그 |
| 비유 | 입주 전 소방 점검 | 입주 후 화재경보기 |

---

## 정리

- **테스트는 배포 전** , **모니터링은 배포 후**다. "에러를 어떻게 알아채나" 는 모니터링 질문이다
- **로그** 는 무슨 일이 있었는지 , **메트릭** 은 얼마나 , **트레이스** 는 어디서
- **Sentry** 같은 에러 추적 도구는 에러를 묶어서 알려주고 , **프론트엔드 에러**도 잡는다
- 로그에는 traceId 를 붙이고 , **개인정보는 남기지 않는다**
- 알람은 **사용자가 느끼는 증상** 기준으로 , 적고 정확하게
- 운영에서 찾은 에러는 **테스트로 만들어** 재발을 막는다

소방 점검도 하고 , 화재경보기도 달아야 안심하고 산다.
