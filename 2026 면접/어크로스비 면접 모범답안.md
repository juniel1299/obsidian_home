## 2. 서류 질문

### 2-1. 엑셀 업로드는 정확히 어떤 기능인가요? (OPEX)

> 사업비·인건비 데이터를 기존에는 담당자가 Excel 컬럼을 수작업으로 정리하고 매크로로 수집했는데, 이 과정에서 데이터 오류가 자주 났습니다.
> 그래서 정해진 Excel 양식을 업로드하면 서버에서 파일을 읽어 행 단위로 검증한 뒤 DB 에 바로 등록하는 기능을 만들었습니다.
> 필수값, 형식 같은 검증에 실패한 행은 등록하지 않고 사용자에게 알려 주도록 했습니다.
> 결과적으로 수작업 정리와 매크로 단계가 사라져 입력 오류가 줄었습니다.

✏️ 사용한 라이브러리(Apache POI 등)와 실패 행 처리 방식(전체 롤백인지, 실패 행만 제외인지)은 실제 구현대로 말할 것.
꼬리질문 대비: "업로드 중 일부 행만 실패하면?" → 트랜잭션 단위(전체 롤백 vs 부분 등록)와 그 선택 이유.

### 2-2. 엑셀 다운로드는 어떤 방식으로 구현했나요? (ELM Portal)

> 처음에는 전체 데이터를 한 번에 조회해서 메모리에 올린 뒤 Excel 로 만들었는데, 데이터가 많아지면서 서버 메모리가 차고 서버가 중단되는 문제가 있었습니다.
> 그래서 전체를 한 번에 가져오지 않고 5,000건 단위로 나눠 조회한 뒤, 조회한 만큼 Excel 에 쓰고 다음 묶음을 조회하는 순차 처리로 바꿨습니다.
> 한 번에 메모리에 올라가는 양이 5,000건으로 제한되니까 전체 건수가 늘어나도 서버가 버틸 수 있게 됐습니다.

꼬리질문 대비:
- "Excel 파일 객체 자체도 메모리에 쌓이지 않나요?" → POI 를 썼다면 `SXSSFWorkbook` 처럼 일정 행 수만 메모리에 두고 나머지는 임시 파일로 내리는 스트리밍 방식이 짝을 이룬다. ✏️ 실제로 썼는지 확인.
- "5,000 은 어떻게 정했나요?" → 메모리 사용량과 조회 횟수(속도) 사이의 절충. ✏️ 실제 측정 근거가 있으면 말하기.

### 2-3. 대시보드 화면에서 데이터는 어떻게 뿌렸나요? (ELM Portal)

> 대시보드 통계는 화면에서 요청할 때마다 원본 데이터를 집계하면 느리기 때문에, Batch 프로그램이 미리 통계 데이터를 만들어 통계 테이블에 쌓아 두게 했습니다.
> 화면은 React 에서 API 를 호출해 이 통계 테이블을 조회하고, 표는 AG Grid, 차트는 ECharts 로 그렸습니다.
> 즉 무거운 집계는 Batch 가, 화면은 가벼운 조회만 하도록 역할을 나눴습니다.

### 2-4. 엑셀 다운로드는 백엔드에서 따로 동작하고, 화면 데이터는 서버사이드 렌더링인가요? (ELM Portal)

> 아닙니다. ELM Portal 은 React 기반 클라이언트 사이드 렌더링(CSR)입니다.
> 화면 데이터는 브라우저에서 React 가 API 를 호출해 JSON 으로 받아 그리고, Excel 다운로드는 별도 API 를 호출하면 서버가 파일을 만들어 응답으로 내려 주는 구조입니다.
> 둘 다 같은 Spring Boot 백엔드의 API 지만, 화면 조회는 OFFSET / FETCH 로 현재 페이지만 가져오고, 다운로드는 5,000건씩 끊어 전체를 처리한다는 점이 다릅니다.

포인트: 면접관이 SSR 로 오해했으니 CSR 이라고 명확히 정정하는 게 좋다. 이 질문이 5번(서버 컴포넌트) 질문으로 이어진다.

## 4. Spring vs Spring Boot 차이

> Spring 은 DI, AOP 같은 핵심 기능을 제공하는 프레임워크고, Spring Boot 는 Spring 을 쉽게 쓰도록 설정을 자동화한 도구입니다.
> Spring 만 쓰면 빈 등록, DispatcherServlet, DataSource 같은 설정을 XML 이나 Java Config 로 직접 해야 하고, 톰캣에 war 로 배포해야 합니다.
> Spring Boot 는 세 가지를 해 줍니다.
> 첫째, **Auto Configuration** 으로 클래스패스에 있는 라이브러리를 보고 필요한 빈을 자동 등록합니다.
> 둘째, **Starter** 의존성으로 관련 라이브러리와 호환 버전을 묶어 줍니다.
> 셋째, **내장 톰캣**이 있어서 jar 하나로 `java -jar` 실행이 됩니다.
> 그래서 Boot 는 Spring 을 대체하는 게 아니라, Spring 위에서 설정과 배포를 단순하게 만든 것입니다.

## 5. Next.js 서버 컴포넌트 vs 클라이언트 컴포넌트

> App Router 에서는 컴포넌트가 기본적으로 서버 컴포넌트고, 파일 맨 위에 `'use client'` 를 쓰면 클라이언트 컴포넌트가 됩니다.
> **서버 컴포넌트**는 서버에서만 실행됩니다. DB 나 API 를 서버에서 바로 조회할 수 있고, 비밀 키를 안전하게 쓸 수 있고, 컴포넌트 JS 코드가 브라우저로 가지 않아 번들이 작아집니다. 대신 `useState`, `useEffect`, `onClick` 같은 상태와 이벤트를 쓸 수 없습니다.
> **클라이언트 컴포넌트**는 서버에서 첫 HTML 을 만든 뒤 브라우저에서 하이드레이션되어 상태, 이벤트, 브라우저 API 를 쓸 수 있습니다.
> 그래서 데이터 조회와 정적인 부분은 서버 컴포넌트로, 버튼·입력처럼 상호작용이 필요한 작은 부분만 클라이언트 컴포넌트로 나누는 게 기본 원칙입니다.

꼬리질문 대비:
- "클라이언트 컴포넌트는 서버에서 안 그려지나요?" → 그려진다. 첫 HTML 은 서버에서 만들고, 브라우저에서 하이드레이션된다. 흔한 오해.
- "서버 컴포넌트에서 클라이언트 컴포넌트로 함수를 props 로 넘길 수 있나요?" → 안 된다. props 는 직렬화 가능한 값만 가능하다. (Server Action 은 예외)

관련 글: [SSR vs CSR](https://problem-child.tistory.com/118)

## 6. NoSQL — 왜 Redis 를 쓰나요?

> 대시보드 조회 속도를 높이려고 Redis 를 **캐시**로 썼습니다.
> 대시보드는 조회 조건이 같으면 결과도 같은데, 매번 DB 에서 조회하면 느렸습니다.
> 그래서 첫 조회 때는 DB 에서 결과를 가져와 Redis 에 저장하고, 두 번째 조회부터는 DB 를 거치지 않고 Redis 에서 바로 응답하도록 했습니다.
> 첫 조회는 시간이 걸리지만, 이후 같은 조회는 빠르게 나옵니다.

용어: 이 방식은 **Cache-Aside(Look-Aside) 패턴**이다. 캐시에 없으면(Cache Miss) DB 조회 후 캐시에 저장하고, 있으면(Cache Hit) 캐시에서 바로 응답한다. 면접에서 이 용어를 한 번 쓰면 좋다.

### 6-1. 대시보드면 데이터가 많은데 왜 Redis 를 썼나요?

면접관 지적이 맞다. Redis 는 데이터를 메모리에 두기 때문에 원본 대용량 데이터를 저장하는 용도가 아니다. 인정하고, "원본이 아니라 조회 결과만 캐싱했다"로 범위를 좁혀 답한다.

> 말씀하신 대로 Redis 는 메모리 기반이라 원본 데이터를 전부 담는 저장소로는 맞지 않습니다.
> 저는 원본 데이터를 Redis 에 넣은 게 아니라, 원본은 DB 에 두고 대시보드에서 반복 조회되는 **조회 결과만** 캐싱했습니다.
> 대시보드는 여러 사용자가 같은 통계를 반복해서 보기 때문에, 첫 조회 결과를 캐싱해 두면 두 번째부터는 DB 를 다시 조회하지 않고 바로 응답할 수 있습니다.
> 다만 지금 다시 본다면 데이터가 갱신될 때 캐시를 비우는 기준과 **TTL** 을 더 명확히 두겠습니다. 예를 들어 통계 Batch 가 끝나는 시점에 캐시를 지우거나, Batch 주기에 맞춰 TTL 을 걸어 오래된 통계가 남지 않게 하겠습니다.

✏️ 실제로 TTL 을 걸었는지, Batch 후 캐시를 지웠는지 확인. 이미 했다면 마지막 문장을 "~하도록 했습니다"로 바꾸기.

꼬리질문 대비:
- "원본 데이터가 바뀌면 캐시는 어떻게 되나요?" → 캐시 무효화 질문이다. TTL 만료 또는 Batch 완료 후 캐시 삭제로 답한다.
- "첫 조회가 느린 건 어떻게 해결하나요?" → Batch 직후 자주 쓰는 조회 조건을 미리 캐시에 넣어 두는 **캐시 워밍(Cache Warming)** 으로 개선할 수 있다.

포인트: 틀린 선택을 방어하지 말고 "지금이라면 이렇게"로 개선안을 보여 주는 게 점수가 높다.

### 6-2. Redis vs MongoDB 차이

> 둘 다 NoSQL 이지만 용도가 다릅니다.
> **Redis** 는 Key-Value 저장소고 데이터를 메모리에 둬서 매우 빠릅니다. 대신 메모리 크기만큼만 저장할 수 있어서 캐시, 세션, 랭킹, 분산 락처럼 작고 자주 읽는 데이터에 씁니다. 디스크 저장(RDB 스냅샷, AOF)은 있지만 보조 수단입니다.
> **MongoDB** 는 JSON 형태의 문서(Document)를 디스크에 저장하는 문서형 DB 입니다. 스키마가 유연하고, 인덱스와 복잡한 조회, 집계 파이프라인을 지원해서 대용량 데이터를 주 저장소로 담을 수 있습니다.
> 정리하면 Redis 는 빠른 임시 저장소(캐시), MongoDB 는 유연한 주 저장소입니다.

### 6-3. (면접관 피드백 정리)

대용량 원본 저장은 DynamoDB, MongoDB 가 맞다. Redis 로 답하려면 "집계 데이터만 TTL 걸어 캐싱" 으로 범위를 좁혀야 한다. → 6-1 답변에 반영했다.

관련 글: [Redis vs MongoDB vs DynamoDB 차이](https://problem-child.tistory.com/132)

## 7. 왜 Django 를 사용해 보셨나요?

> 실무에서 계속 Spring 만 써 왔기 때문에, 다른 언어와 프레임워크는 같은 문제를 어떻게 푸는지 직접 경험해 보고 싶어서 Django 를 써 봤습니다.
> Django 는 ORM, 관리자 페이지, 인증이 기본으로 들어 있어서 설정 없이 빠르게 기능을 만들 수 있었습니다.
> 써 보니 Spring 의 Controller-Service-Repository 구조와 Django 의 MTV(Model-Template-View) 구조가 이름은 달라도 역할 분리는 비슷해서 빠르게 적응할 수 있었습니다.
> 이 경험으로 프레임워크가 바뀌어도 요청 처리, 데이터 접근, 화면을 나누는 원리는 같다는 걸 알게 됐고, 새 기술도 빨리 익힐 수 있다는 자신감이 생겼습니다.

포인트: "Spring 만 써서"가 약점처럼 들리지 않게, **익숙한 것에 머무르지 않고 새 기술을 직접 써 본다**는 태도로 연결. 어크로스비가 React, Vue, Svelte 를 같이 쓰는 회사라 이 메시지가 잘 맞는다.

꼬리질문 대비: "Django 랑 Spring 중 뭐가 더 좋았나요?" → 우열보다 용도. Django 는 빠른 개발과 Python 생태계(AI, 데이터), Spring 은 타입 안정성과 대규모 엔터프라이즈 구조에 강하다.

용어 대응표:

| Spring | Django | 역할 |
|---|---|---|
| Controller | View | 요청 받고 응답 |
| JSP / React 화면 | Template | 화면 |
| Entity + Repository (JPA, MyBatis) | Model (ORM) | 데이터 접근 |

## 8. 치이카와 앱은 다 못 만드셨나요? (GitHub)

> 네, 지금은 일시중지한 상태입니다.
> 증강현실(AR) 구현과 위치 추적 기능에서 문제가 있었는데, 둘 다 웹 개발과 다른 기기·센서 영역이라 해결에 생각보다 시간이 많이 들었습니다.
> 이 프로젝트를 하면서 처음부터 어려운 기능을 한꺼번에 넣으면 핵심 기능까지 완성하지 못한다는 걸 배웠습니다.
> 그래서 이후 사이드 프로젝트는 핵심 기능만 담은 MVP 를 먼저 끝까지 완성하고, 어려운 기능은 그다음에 하나씩 붙이는 방식으로 진행하고 있습니다.

✏️ AR·위치 추적에서 구체적으로 어떤 문제가 있었는지 한 줄로 준비해 둘 것 (예: 기기마다 위치 오차가 컸다, AR 라이브러리가 웹에서 지원이 부족했다). 면접관이 "어떤 문제였나요?" 라고 반드시 묻는다.

포인트: 미완성 레포는 면접관이 "끝까지 해내는 사람인가"를 확인하는 질문이다. 변명보다 **배운 점 + 지금은 어떻게 다르게 하는지**가 핵심. 현재 기획 중인 '다음자리'(예약·대기열 서비스)처럼 범위를 좁힌 프로젝트를 예시로 들 수 있다.
GitHub 정리 팁: 미완성 레포는 README 에 "진행 상태 / 중단 사유"를 적어 두거나 비공개로 돌린다.

## 9. DB 설계할 때 무엇을 고려하나요?

> 크게 네 가지를 봅니다.
> 첫째, **요구사항과 조회 패턴**입니다. 어떤 화면에서 어떤 조건으로 많이 조회하는지를 먼저 봐야 테이블과 인덱스를 정할 수 있습니다.
> 둘째, **정규화**입니다. 중복 데이터를 줄여 수정 시 불일치를 막고, 조회 성능이 꼭 필요한 곳만 의도적으로 반정규화합니다. 예를 들어 대시보드 통계는 원본에서 매번 집계하지 않고 Batch 로 만든 통계 테이블에 따로 저장했습니다.
> 셋째, **PK 와 제약조건**입니다. 바뀌지 않는 값을 PK 로 두고, FK, NOT NULL, UNIQUE 로 잘못된 데이터가 DB 단에서 들어오지 못하게 합니다.
> 넷째, **인덱스**입니다. WHERE, JOIN, ORDER BY 에 자주 쓰는 컬럼에 인덱스를 두되, 인덱스가 많으면 INSERT·UPDATE 가 느려지므로 조회 빈도와 함께 판단합니다.

관련 글: DB 설계할 때 고려할 것 (ft. 이사 짐 싸기) — 발행했다면 링크 추가.

## 10. 프로그램 개발 설계는 어떻게 진행하나요?

> 1. **요구사항 분석**: 기획·현업과 기능 범위, 예외 상황, 권한을 먼저 확정합니다.
> 2. **데이터 설계**: 필요한 테이블과 조회 쿼리를 먼저 정합니다. 데이터 구조가 정해져야 API 와 화면이 흔들리지 않습니다.
> 3. **API 설계**: 요청·응답 형식을 정하고, 협업할 때는 이 형식을 먼저 맞춘 뒤 각자 개발합니다.
> 4. **공통화 검토**: 이미 있는 공통 컴포넌트나 공통 로직을 쓸 수 있는지, 새로 만들 기능이 다른 화면에도 반복될지를 봅니다.
> 5. **개발 → 테스트 → 리뷰 → 배포** 순서로 진행합니다.
> 실제로 후배 개발자와 협업할 때 데이터 형식과 기능 연결 지점을 먼저 맞추고 나서 각자 개발하니까 통합 단계에서 수정이 크게 줄었습니다.

## 11. 에러 발생 시 어떤 도구로 발견하고 알람을 받나요?

질문 의도: 모니터링 / 알림 도구(Sentry, Grafana, Slack 알림 등)를 묻는 질문일 가능성이 높다. JUnit 은 배포 **전** 테스트 도구라서 운영 중 에러 알림과는 다르다. 두 가지를 구분해서 답한다.

> 운영 중에는 별도 모니터링 도구 대신, 서버에서 에러가 발생하면 에러 로그를 저장하고 이를 조회하는 **관리 화면**에서 확인하는 구조였습니다.
> 그래서 에러를 확인할 수는 있었지만, 담당자가 화면에 들어가 봐야 알 수 있어서 실시간으로 알림을 받지는 못했습니다.
> 이 부분이 아쉬웠기 때문에, 서비스 환경이라면 프론트는 Sentry 로 브라우저 에러를 수집하고, 서버 에러는 Slack 같은 메신저로 바로 알림이 오도록 구성하고 싶습니다.
> 배포 전에는 백엔드 JUnit, 프론트 Jest 같은 테스트로 에러를 미리 줄이는 것도 함께 가져가야 한다고 생각합니다.

✏️ 에러 로그 화면의 구조(에러를 DB 테이블에 쌓았는지, 로그 파일을 읽어 보여 줬는지)를 한 줄로 준비. "어떻게 로그를 화면에 보여 줬나요?"가 꼬리질문으로 나올 수 있다.

포인트: 안 써 본 도구를 써 봤다고 하지 말 것. "써 본 것"과 "알고 있고 도입하고 싶은 것"을 분리.

키워드 정리:
- **JUnit**: Java 단위 테스트. `@Test`, `assertEquals`. Spring 은 `@SpringBootTest` 로 통합 테스트.
- **Jest**: JS / React 단위 테스트. React Testing Library 와 함께 컴포넌트 테스트.
- **TDD**: 실패하는 테스트 먼저 작성(Red) → 통과하는 최소 코드(Green) → 리팩터링(Refactor).

## 12. 검색 품질 향상은 어떤 걸 말하나요? (블로그 챗봇)

> 블로그 챗봇은 질문을 받으면 관련 블로그 글을 찾아서 그 내용을 바탕으로 답합니다.
> 답변 품질은 **관련 글을 얼마나 정확히 찾아오느냐**에 달려 있어서, 이 검색 단계를 두 가지로 개선했습니다.
> 첫째, **글 내용에서 핵심 단어를 뽑아** 검색에 활용했습니다. 질문 단어가 글의 핵심 단어와 맞으면 그 글이 더 잘 찾아지도록 했습니다.
> 둘째, 답변과 함께 나온 연관 문서에 **좋아요·싫어요 버튼**을 두고, 사용자 피드백을 문서의 **가중치**로 반영했습니다. 좋아요를 많이 받은 문서는 다음 검색에서 더 위로, 싫어요를 받은 문서는 아래로 가도록 했습니다.
> 사용자가 실제로 도움이 됐다고 평가한 문서가 다시 잘 나오도록, 검색 결과가 쓰일수록 나아지는 구조를 만든 것입니다.

✏️ 준비할 것:
- 핵심 단어를 어떻게 뽑았는지 (형태소 분석, 태그, 빈도 등)
- 가중치를 검색 점수에 어떻게 섞었는지 (예: 검색 점수 + 좋아요 비율 × 계수)

꼬리질문 대비:
- "싫어요를 악의적으로 누르면요?" → 한 사용자당 문서별 1회로 제한, 가중치에 상한·하한을 둔다.
- "새 글은 피드백이 없어서 불리하지 않나요?" → 콜드 스타트 문제. 새 글은 피드백이 일정 수 쌓이기 전까지 가중치 영향을 적게 주는 식으로 보완할 수 있다.

## 13. 공통 컴포넌트 제작 방식 (P2SearchArea, P2FormArea)

> ELM Portal 은 대부분 화면이 "검색 영역 + Grid" 또는 "입력 Form" 구조라서, 화면마다 검색 조건과 Form 을 따로 만들면 코드가 반복되고 화면별로 동작이 달라졌습니다.
> 그래서 검색 영역(P2SearchArea)과 Form 영역(P2FormArea)을 공통 컴포넌트로 만들고, 각 화면은 **필드 목록을 설정 값(props)으로 넘기기만** 하면 입력 타입, 레이아웃, 초기화, 검색 이벤트가 같은 방식으로 동작하게 했습니다.
> 새 화면은 설정만 작성하면 되니 개발 시간이 줄었고, 수정도 공통 컴포넌트 한 곳만 고치면 전체 화면에 반영됐습니다.

✏️ 실제 props 구조(예: `fields` 배열에 `type`, `name`, `label`)를 한 줄로 예시 들 수 있게 준비.

### 13-1. 다른 프로젝트에도 적용해 봤나요?

✏️ 실제 여부대로. 적용 안 했다면:

> 아직 다른 프로젝트에는 적용하지 않았고 ELM Portal 안의 여러 화면에서 재사용했습니다.
> 다만 다른 프로젝트에 가져가려면 프로젝트 전용 로직(공통 코드 조회 API, 권한 처리)을 분리하고, 순수 UI 부분만 별도 패키지로 빼야 한다고 생각합니다.

### 13-2. 수정이 생기면 어떻게 배포했나요?

> 같은 프로젝트 안의 공통 폴더에 있는 컴포넌트라 별도 배포 없이 프로젝트 빌드·배포에 함께 포함됐습니다.
> 대신 공통 컴포넌트 수정은 쓰는 화면 전체에 영향이 가기 때문에, 기존 props 동작은 유지하고 새 기능은 옵션 props 로 추가하는 방식으로 하위 호환을 지켰고, 수정 후에는 사용하는 주요 화면을 확인했습니다.
> 여러 프로젝트가 공유하게 되면 사내 npm 패키지로 분리해서 버전(Semantic Versioning)으로 관리하는 게 맞다고 봅니다.

✏️ 실제 배포 절차와 다르면 수정.

## 15. GET vs POST 차이

> **GET** 은 데이터를 **조회**할 때 씁니다. 데이터를 URL 쿼리스트링에 담아 보내고, 같은 요청을 여러 번 보내도 결과가 같아(멱등) 브라우저나 서버가 캐싱할 수 있습니다. URL 에 노출되므로 민감 정보를 담으면 안 됩니다.
> **POST** 는 데이터를 **생성**하거나 서버 상태를 바꿀 때 씁니다. 데이터를 Body 에 담아 보내고, 같은 요청을 두 번 보내면 데이터가 두 번 생길 수 있어 멱등하지 않고, 기본적으로 캐싱하지 않습니다.

꼬리질문 대비: "POST 는 Body 에 넣으니 안전한가요?" → 아니다. URL 에 안 보일 뿐, 암호화는 HTTPS 가 한다.

## 16. PUT vs PATCH 차이

> 원본 노트의 "Put fetch" 는 **PUT vs PATCH** 로 보인다. (`fetch` 는 HTTP 메서드가 아니라 브라우저의 요청 함수다.)

> 둘 다 수정에 쓰지만 범위가 다릅니다.
> **PUT** 은 리소스를 **통째로 교체**합니다. 보내지 않은 필드는 비워지거나 기본값이 될 수 있어서 전체 데이터를 보내야 합니다. 같은 요청을 여러 번 보내도 결과가 같아 멱등합니다.
> **PATCH** 는 **바꿀 필드만** 보내 부분 수정합니다. 보내는 데이터가 적고, 구현에 따라 멱등이 아닐 수 있습니다. 예를 들어 "조회수 +1" 같은 PATCH 는 보낼 때마다 결과가 달라집니다.
> 예: 회원 정보에서 닉네임만 바꾸면 PATCH, 프로필 전체를 새로 저장하면 PUT 입니다.

만약 정말 "fetch" 를 물은 거라면:

> `fetch` 는 브라우저 내장 HTTP 요청 함수로 Promise 를 반환합니다. axios 와 달리 4xx·5xx 응답에도 reject 하지 않아서 `response.ok` 를 직접 확인해야 하고, JSON 변환(`response.json()`)도 직접 해야 합니다.

## 17. Zustand 를 어떻게 쓰고 있나요?

> ELM Portal 에서 여러 화면이 공유하는 상태를 Zustand 로 관리했습니다.
> [✏️ 실제로 store 에 둔 것: 예) 로그인 사용자 정보와 권한, 메뉴 정보, 공통 코드]
> `create` 로 store 를 만들고, 컴포넌트에서는 `useStore(state => state.user)` 처럼 **필요한 값만 selector 로 꺼내 써서** 그 값이 바뀔 때만 리렌더링되게 했습니다.
> 서버에서 받아온 화면 데이터나 한 화면에서만 쓰는 값은 전역에 넣지 않고 컴포넌트 상태로 두어, 전역 store 가 커지지 않게 했습니다.

### 17-1. 왜 Zustand 를 쓰나요? (Zustand vs Redux)

> Redux 는 action, reducer, store 를 나눠 작성해야 해서 코드가 많고 설정이 복잡합니다. 대신 상태 변경 흐름이 엄격하게 정해져 있고 DevTools, 미들웨어 생태계가 강해서 대규모 팀에 유리합니다.
> Zustand 는 store 하나를 함수로 만들고 훅으로 바로 쓰면 돼서 코드가 훨씬 적고, Provider 로 앱을 감쌀 필요도 없습니다.
> ELM Portal 은 전역 상태가 사용자·권한·메뉴 정도로 단순했기 때문에, Redux 의 구조가 주는 이점보다 보일러플레이트 비용이 더 크다고 판단해 Zustand 를 썼습니다.

✏️ Zustand 를 직접 선택했는지, 프로젝트에 이미 정해져 있었는지에 따라 마지막 문장 수정. 이미 정해져 있었다면 "도입 이유를 이해하고 쓰고 있다"로.

## 18. 풀스택이면 API 호출 시 프론트가 만들 데이터와 백이 줄 데이터를 어떻게 나누나요?

> 기준은 **"데이터의 정확성과 보안이 필요한가, 화면 표현인가"** 입니다.
> **백엔드**: 권한 체크, 비즈니스 규칙, 계산·집계, 필터링·정렬·페이징처럼 결과가 정확해야 하거나 대량 데이터를 다루는 것은 서버에서 합니다. 프론트 값은 사용자가 조작할 수 있기 때문에 금액이나 권한은 반드시 서버에서 다시 검증합니다.
> **프론트엔드**: 날짜·숫자 포맷, 정렬된 데이터를 차트 형태로 바꾸기, 입력 즉시 보여 주는 검증처럼 화면 표현과 사용자 경험에 관한 것은 프론트에서 합니다.
> 실제로 ELM Portal 에서는 페이징을 OFFSET / FETCH 로 DB 에서 처리해서 필요한 만큼만 내려 주고, Grid 의 표시 형태는 프론트에서 구성했습니다.
> 보안 컬럼은 로그인 정보를 기준으로 화면에서 노출을 제어했는데, 지금 보면 이 부분은 서버에서 처리하는 게 더 맞다고 생각합니다. 화면에서 컬럼을 숨겨도 API 응답에는 데이터가 남아 있어서 개발자 도구로 볼 수 있기 때문입니다. 다시 한다면 서버에서 권한을 확인해 응답에서 보안 컬럼 자체를 빼겠습니다.

포인트: 면접관이 "화면에서만 숨기면 안전한가요?"라고 먼저 찌르기 전에 **스스로 한계를 말하고 개선안을 제시**하는 게 훨씬 낫다.

## 19. 권한관리 보안은 어떻게 하고 있나요?

> 인증과 인가를 나눠서 말씀드리겠습니다.
> **인증**은 로그인한 사용자가 누구인지 확인하는 것으로, ELM Portal 은 회사 계정 하나로 여러 사내 시스템에 로그인하는 **SSO** 방식이었습니다. 시스템이 비밀번호를 직접 다루지 않고, SSO 서버가 인증한 사용자 정보를 받아 로그인 처리했습니다.
> **인가**는 그 사용자가 무엇을 할 수 있는지로, 로그인 사용자 정보와 권한을 기준으로 메뉴 접근과 AG Grid 보안 컬럼 노출을 제어했습니다.
> 다만 보안 컬럼은 화면에서 숨기는 방식이라, 지금 다시 한다면 API 에서도 권한을 확인해 응답에서 데이터를 빼겠습니다. 화면 제어는 개발자 도구나 API 직접 호출로 우회할 수 있기 때문입니다.

꼬리질문 대비: "SSO 는 어떻게 동작하나요?" → 사용자가 시스템에 접속하면 SSO 인증 서버로 보내지고, 인증되면 토큰(또는 티켓)을 받아 다시 시스템으로 돌아온다. 시스템은 이 토큰을 검증해 사용자를 식별한다. 한 번 로그인하면 같은 SSO 를 쓰는 다른 시스템도 다시 로그인하지 않는다.

✏️ 19-1 의 "JWT 를 HttpOnly 쿠키에 담는다"는 ELM Portal(SSO)이 아니라 다른 프로젝트 이야기라면, 어떤 프로젝트였는지 먼저 말하고 답할 것.

### 19-1. JWT 를 HttpOnly 쿠키에 담는다고 했는데 왜 그렇게 하나요?

> **XSS 로 토큰을 탈취당하지 않기 위해서**입니다.
> localStorage 에 토큰을 저장하면 JavaScript 로 읽을 수 있어서, 악성 스크립트가 주입되면 `localStorage.getItem` 으로 토큰을 훔쳐 갈 수 있습니다.
> HttpOnly 쿠키는 JavaScript 에서 접근할 수 없고 브라우저가 요청에 자동으로 붙여 보내기만 하므로, 스크립트가 토큰 값을 읽을 수 없습니다.
> 대신 쿠키는 자동 전송되기 때문에 **CSRF** 에 노출됩니다. 그래서 `SameSite` 속성(Lax 또는 Strict)과 `Secure`(HTTPS 에서만 전송)를 함께 설정하고, 필요하면 CSRF 토큰을 씁니다.
> 또 Access Token 은 만료 시간을 짧게 두고 Refresh Token 으로 재발급해서, 토큰이 유출돼도 피해 시간을 줄입니다.

포인트: HttpOnly 가 XSS 자체를 막는 건 아니다. "스크립트가 실행돼도 토큰 값을 읽어 가지 못하게 한다"까지만 말할 것.

| 저장 위치 | XSS 로 탈취 | CSRF | 대응 |
|---|---|---|---|
| localStorage | 위험 (JS 로 읽힘) | 안전 (자동 전송 안 됨) | XSS 방어에 의존 |
| HttpOnly 쿠키 | 값은 못 읽음 | 위험 (자동 전송) | SameSite, Secure, CSRF 토큰 |
