## 검증 기준

- 정원 1석에 여러 계정이 동시에 예약해도 1건만 확정된다. 같은 계정의 중복 요청으로 활성 신청이 늘어나지 않는다.
- 동시 취소·신규 예약에서도 기존 대기자가 순서대로 한 번만 승격된다. 취소와 승격 사이에서 실패하면 일부만 반영되지 않는다.
- 참가자와 운영자 권한을 구분한다. 참가자는 명단 전체를 볼 수 없고, 운영자는 담당 회차만 관리한다.
- 연결 복구 후 서버 상태와 화면이 일치한다. 키보드로 예약 흐름을 완료하고 상태 변화를 보조 기술로 확인할 수 있다.
- 부하 시험에는 동시 요청 수, p95 응답 시간, 오류율, 정원·순번 위반 수를 남긴다. 정원·순번 위반 허용치는 0건이며 속도 목표는 시험 전에 정한다.
- 포트폴리오 증거: 프런트엔드는 상태 갱신·접근성 시연, 백엔드는 동시성·실패 복구 결과, 풀스택은 배포된 사용자 흐름과 운영 지표를 남긴다.

## Claude Code 첫 구현 지시서의 선행 조건

1. 제목과 대상 도메인, 단일 스터디 운영 범위, 계정·권한 모델, 마감과 자동 확정 정책을 결정한다.
2. 회차·신청 상태 전이표와 정원·중복 불변조건을 정한다. 정원 초과, 중복 요청, 마감, 취소 뒤 재신청의 응답을 API 계약에 적는다.
3. 구현 저장소 위치, 기본 스택, 로컬 실행 환경, 샘플 회차와 계정, 통합 테스트 실행 방법을 지정한다.
4. 첫 작업 범위는 회차 등록·조회와 정원 내 예약·취소로 제한한다. 마감, 권한, 마지막 한 자리 동시 요청의 인수 기준을 포함한다. 대기·승격은 후속 작업으로 분리하되 첫 작업의 데이터 모델이 이를 막지 않는지 검토한다.
